# Feature Specification: Cloudflare Online Multiplayer

Created: 2026-07-11
Status: Design approved; awaiting written-spec review
Workflow phase: Feature specification

## Problem

Catan Imitation currently supports a complete local hot-seat game, but players cannot join from separate browsers. Online play must preserve the existing rules, public player trading, English/Chinese interface, and Commerce Guild expansion without requiring the project owner to purchase or maintain a traditional server.

The online version must not trust a browser to choose random outcomes, impersonate another player, mutate shared state, or receive opponents' private information.

## Users and Actors

- Room host: creates a private room, shares its code, and starts the game after all players are ready.
- Online player: joins one seat from one or more browser tabs and controls only that seat.
- Reconnecting player: returns to the same seat from the original browser within the retention window.
- Local player: continues to use the existing single-browser hot-seat mode without Cloudflare connectivity.
- Reviewer or operator: deploys from GitHub, inspects Cloudflare logs, and verifies privacy and recovery behavior.

## Approved Product Scope

### In Scope

- Keep the existing local hot-seat mode as a first-class entry point.
- Add an online-game entry point with anonymous nicknames and private invitation codes.
- Support three or four online players using the existing deterministic board and port layout.
- Give each browser one authenticated player seat and hide opponents' private resources, development cards, hidden victory points, and unresolved auction bids.
- Let the host start after three or four seated players are ready; lock seats when play begins.
- Run the complete current ruleset online, including setup, robber flow, development cards, ports, public player trades, and the full Commerce Guild expansion.
- Preserve a room for 24 hours after its last valid activity and let the original browser reconnect with a seat credential.
- Allow play to continue while a non-required player is offline; wait when the rules require that player's decision.
- Serve the React application, HTTP API, WebSocket endpoint, and room Durable Objects as one Cloudflare Worker deployment.
- Deploy production from the GitHub `main` branch using Cloudflare Workers Builds.
- Correct the Commerce Guild auction deadlock when nobody has a positive bid.

### Out of Scope

- User accounts, passwords, social login, cross-device seat recovery, profiles, friends, rankings, or long-term match history.
- Public room browsing, matchmaking, spectators, text chat, voice chat, reactions, or moderation tools.
- Two-player variants, more than four players, AI replacement players, or mid-game seat replacement.
- Randomized terrain, number-token, or port layouts.
- Turn timers, forced skips, automatic strategic choices, or automated bids for disconnected players.
- Full event sourcing, D1, KV, R2, analytics warehousing, or indefinite game storage.
- Simultaneously maintaining GitHub Pages and Cloudflare as separate production applications.

## User Stories

### US1: Create and Start a Private Room

As a host, I can create a room, share a six-character invitation code, see three or four players become ready, and manually start the game so that a private group can begin together.

Independent acceptance:

- A new room returns a host seat and invitation code.
- Nicknames are unique within a room after case normalization.
- The room rejects a fifth player and rejects new seats after the game starts.
- Start is available only to the host when all three or four seated players are ready.

### US2: Play an Authoritative Private Game

As a player, I can send game choices from my own seat while the server validates and broadcasts the resulting state, so that no client can impersonate another player or choose illegal/random results.

Independent acceptance:

- The server derives the acting player from the authenticated seat.
- Dice, robber thefts, shuffled cards, and blind-box outcomes are generated by the authoritative runtime.
- Duplicate and stale commands cannot apply twice.
- Existing local and online modes use the same pure match-transition implementation.

### US3: Preserve Hidden Information

As a player, I can see my own cards and resources without receiving opponents' private details, so that online play retains meaningful hidden information.

Independent acceptance:

- Opponent projections contain resource and development-card counts but not their types.
- Hidden victory-point cards do not appear in opponents' visible scores before game end.
- Pending auction bid amounts are visible only to the bidder and authoritative room.
- A blind-box development-card type is visible only to its recipient.

### US4: Recover From Disconnection

As a player using the original browser, I can refresh or reconnect within 24 hours and receive the current seat-specific state, so that a temporary connection failure does not end the game.

Independent acceptance:

- A reconnect uses a secret seat credential, not the invitation code.
- Reconnect always returns a complete current projection rather than replaying assumed missing messages.
- Non-required offline players do not freeze unrelated actions.
- The game waits rather than choosing automatically when an offline player's input is required.

### US5: Complete Commerce Guild Auctions

As an online or local player, I can submit a sealed bid or pass and every auction reaches a legal next state, including when nobody has tokens or every player passes.

Independent acceptance:

- Opening an auction when all players have zero guild tokens completes the auction phase immediately.
- If players could bid but all submit zero in a round, the box has no winner and the round advances without consuming tokens or generating a reward.
- A positive winning bid retains the current highest-bid and active-turn-order tie rules.
- Online bid values remain sealed until resolution; losing bid values are not published after resolution.

## Functional Requirements

### Mode and Lobby

- OM-001: The application must present Local Game and Online Game as peer entry points.
- OM-002: Local Game must remain playable without a network connection or Cloudflare room.
- OM-003: Creating a room must allocate a host seat and a six-character uppercase code that excludes visually ambiguous characters.
- OM-004: Joining must accept a trimmed nickname from 1 through 20 characters and enforce case-insensitive uniqueness in the room.
- OM-005: A lobby must allow three or four seats, per-seat ready state, voluntary departure before start, and host transfer to the earliest joined connected player when the host leaves.
- OM-006: Only the host may start, and only when all seated players are ready and the seated count is three or four.
- OM-007: Starting must lock the seat roster. After start, no seat may leave, be replaced, or be newly allocated.

### Anonymous Seat Identity

- OM-008: Seat creation must return a public seat ID and a high-entropy secret seat token.
- OM-009: The browser must retain the seat token in origin-local storage keyed by room code; clearing storage or changing devices is an explicit unrecoverable case for the first version.
- OM-010: Persistent storage must contain only a one-way token hash, never the seat-token plaintext.
- OM-011: Invitation codes must locate rooms but must never authenticate an existing seat.
- OM-012: A valid seat token must be exchanged over authenticated HTTPS for a single-use WebSocket ticket with an approximately 30-second lifetime.
- OM-013: Long-lived seat tokens must not appear in URLs, application logs, broadcasts, or client-visible error details.
- OM-014: Multiple tabs may connect to the same authenticated seat; command idempotency and room versions must prevent duplicate state transitions.

### Room Lifecycle and Recovery

- OM-015: Room lifecycle must be modeled independently as `lobby`, `playing`, `finished`, or `expired`; network lifecycle must not be added to core `GameState.phase`.
- OM-016: A room must refresh its last-activity time on valid commands, connections, and reconnections.
- OM-017: A room with no active connections must expire 24 hours after last activity; an expiry alarm must defer cleanup while connections remain active.
- OM-018: Expiry must delete the room snapshot, credentials, and pending secret inputs.
- OM-019: Reconnect must issue a complete current seat projection and room version.
- OM-020: Presence must be derived from active WebSockets and must not become game-rule state.
- OM-021: A non-required offline seat must not block play; a required offline decision must produce an explicit wait state without automatic input.

### Authoritative Commands

- OM-022: A shared pure `MatchState` transition boundary must own gameplay, Commerce Guild, dice, last public trade, and other synchronized state.
- OM-023: Browser-only selections, panels, locale, and recoverable notices must remain in `UiState` and must not be persisted as room state.
- OM-024: Local and online modes must call the same match transition owner; the online backend must not reimplement rules.
- OM-025: A network command must include a unique command ID, expected room version, action type, and bounded payload.
- OM-026: A client command must not specify its acting player. The room must derive the actor from the authenticated seat and map it to the domain command.
- OM-027: The room must validate the protocol, authenticate the seat, detect duplicate commands, compare the expected version, execute the transition, increment the version, persist, project, and broadcast in that order.
- OM-028: Repeating an accepted command ID must not repeat a transfer, purchase, build, roll, or other transition.
- OM-029: A stale version must return the latest caller-specific projection and require user reconfirmation instead of applying the action speculatively.
- OM-030: Random operations must use an injectable source: deterministic in tests and a server-side cryptographic source online. Clients may not supply dice or randomness.

### State Projection and Privacy

- OM-031: A room must never serialize and send its raw `MatchState` to a browser.
- OM-032: Every accepted transition must produce a caller-specific full projection containing schema version, room version, lifecycle, public state, private state, presence, and acknowledged command ID.
- OM-033: Public state may include board state, turn/phase, waiting requirements, public scores, resource-card counts, development-card counts, bank stock, guild-token/voucher counts, public offers, and privacy-safe logs.
- OM-034: Private state may include only the authenticated seat's resource types, development-card identities, and pending private choices.
- OM-035: Opponent resources, development-card identities, hidden victory points, unresolved bids, and private error detail must not be inferable from projections or log parameters.
- OM-036: Bid-submission status may be public, but bid amounts must remain private. After resolution, publish only the winner, winning amount, and privacy-safe outcome.
- OM-037: A blind-box development-card result must be described publicly as one development card while its type is revealed only to the recipient.

### Commerce Guild Auction Progress

- OM-038: `openGuildAuction` must not enter an unwinnable auction when every player has zero guild tokens; it must move gathering directly to complete and record a structured no-eligible-bidders log.
- OM-039: Online bidding must accept one sealed non-negative whole-number bid per seat, with zero representing pass, and must allow replacement before all seats have submitted.
- OM-040: When all seats submit for a round, at least one positive bid must resolve through the existing winner/reward rule.
- OM-041: When all submitted bids are zero, the round must advance with no winner, payment, or random outcome; after round three, gathering must complete.
- OM-042: Pending bids must survive Durable Object hibernation/restart and must be cleared immediately after round resolution or room expiry.
- OM-043: The corrected no-bid transitions must be shared by Local Game and Online Game, replacing the current rule that rejects every all-zero bid map.

### Client Protocol and Experience

- OM-044: The first version must send complete caller-specific projections after accepted commands; it must not introduce JSON Patch or full event sourcing.
- OM-045: The client must expose connecting, connected, reconnecting, offline, expired, and incompatible states.
- OM-046: Offline controls must be disabled and must not perform optimistic gameplay mutations.
- OM-047: Reconnect attempts must use capped exponential backoff and acquire a new single-use connection ticket.
- OM-048: The online table must reuse current board and bounded feature panels while showing only the authenticated seat's private hand.
- OM-049: The table must continuously expose room code, connection state, seat presence, and any player whose decision is awaited.
- OM-050: Secret auction UI must show the caller's bid and other seats' submission status, never their values.
- OM-051: English-default and Simplified-Chinese switching must remain available in both modes.

### Persistence, Security, and Errors

- OM-052: Each SQLite-backed Durable Object must persist a versioned room record containing lifecycle, timestamps, seats, match snapshot, room version, bounded processed-command IDs, and pending secret bids.
- OM-053: Processed command and audit storage must be bounded and must not retain credentials, private card/resource state, or losing bid values as diagnostic metadata.
- OM-054: Protocol fields, message size, resource quantities, bid amounts, arrays, and strings must be bounded at the network boundary and validated again by the domain owner where applicable.
- OM-055: Same-origin production requests must be enforced, and a strict Content Security Policy must avoid unnecessary third-party scripts.
- OM-056: Per-seat short-window command throttling must reject abusive bursts without corrupting room state.
- OM-057: Errors must use stable translatable codes: `ROOM_NOT_FOUND`, `ROOM_FULL`, `ROOM_ALREADY_STARTED`, `SEAT_TOKEN_INVALID`, `CONNECTION_TICKET_EXPIRED`, `VERSION_CONFLICT`, `COMMAND_NOT_ALLOWED`, `RULE_VIOLATION`, `RATE_LIMITED`, `ROOM_EXPIRED`, `PROTOCOL_INCOMPATIBLE`, and `INTERNAL_ERROR`.
- OM-058: Internal exceptions must expose only a generic client message; logs may include command type, version, duration, and safe error code but never secrets or private state.
- OM-059: Stored `schemaVersion` and wire `schemaVersion` must support explicit compatibility checks. Unsafe state upgrades must terminate the room with an incompatible-version result rather than continue with a partial conversion.

### Hosting and Delivery

- OM-060: Production must be one Cloudflare Worker deployment containing Vite static assets, API routes, WebSocket routing, and a SQLite-backed room Durable Object binding.
- OM-061: Static assets must use SPA fallback, while `/api/*` and WebSocket routes must invoke Worker code before asset routing.
- OM-062: Durable Object class creation must use an explicit Wrangler SQLite migration tag.
- OM-063: GitHub must remain the source repository, and Cloudflare Workers Builds must deploy the production Worker from `main` after verification.
- OM-064: The GitHub Pages production workflow must remain until the Cloudflare preview and production address are verified, then be disabled or removed to prevent two production versions.
- OM-065: English and Chinese READMEs must document Local Game, Online Game, Cloudflare deployment, anonymous-seat limitations, and the current production URL.

## Approved Architecture

```text
Browser
  |-- Local Game --> local reducer --> shared match transition
  `-- Online Game --> HTTPS / WebSocket
                         |
                  Cloudflare Worker
                    |-- Vite static assets
                    |-- room/session API
                    `-- Room Durable Object (one per room code)
                           |-- authenticated command pipeline
                           |-- shared match transition
                           |-- per-seat projections
                           |-- hibernatable WebSockets
                           `-- SQLite snapshot and expiry alarm
```

The Worker entry is a thin router. The Room Durable Object owns room orchestration but delegates game behavior to the shared pure transition. Projection code is the only owner allowed to turn authoritative state into client state. Browser controllers consume projections and dispatch commands but never mutate online gameplay locally.

## Stored Room Model

The stored record contains:

- `schemaVersion`
- `roomCode`
- `lifecycle`
- `createdAt`, `lastActivityAt`, and `expiresAt`
- `hostSeatId`
- seat IDs, nicknames, join order, readiness, player mapping, and token hashes
- authoritative `matchState`
- monotonically increasing `roomVersion`
- a bounded per-seat command-id window
- current sealed-bid submissions while an auction round is open

WebSocket objects and derived presence are never serialized into the record.

## Protocol Behavior

### HTTP

- Create room.
- Join room.
- Leave lobby seat.
- Exchange a valid seat token for a short-lived, single-use WebSocket ticket.

### WebSocket Client Messages

- `room.ready`
- `room.start`
- `match.command`
- `auction.submitBid`
- `connection.heartbeat`

### WebSocket Server Messages

- `room.snapshot`
- `command.rejected`
- `presence.changed`
- `room.expired`
- `protocol.incompatible`

Unknown or oversized messages are rejected without entering the match transition. Successful changes broadcast a fresh seat-specific projection. Rule errors return only to the sender.

## Error and Recovery Behavior

- Recoverable rule and validation errors keep the current projection mounted.
- Version conflict returns the newest caller projection and does not apply the stale command.
- Temporary disconnect disables commands and enters capped reconnect backoff.
- Room expiry and protocol incompatibility stop reconnect attempts and provide a clear return-to-home action.
- An authoritative internal error does not increment the room version or persist a partial transition.

## Verification Requirements

### Domain and Transition Tests

- Preserve all existing rule tests.
- Prove local and online adapters use the same transition result.
- Inject deterministic randomness for dice, theft, decks, and blind boxes.
- Cover zero-token immediate auction completion and three all-pass rounds.
- Preserve positive-bid tie, payment, reward, and bank-accounting behavior.

### Privacy Projection Tests

- Prove opponent resources and development-card identities are absent.
- Prove hidden victory points are absent before game end.
- Prove pending and losing bid amounts are absent.
- Prove development-card blind-box type is visible only to its recipient.
- Inspect structured logs for indirect private-data leakage.

### Room Integration Tests

- Create, join, ready, host-transfer, and start three/four-player rooms.
- Reject duplicate names, over-capacity joins, invalid tickets, and post-start joins.
- Prove actor derivation, version conflict, command idempotency, rate limiting, and atomic persistence.
- Restore snapshots and pending bids after Durable Object restart or hibernation.
- Derive presence across multiple tabs and reconnect a seat.
- Delete inactive rooms through the 24-hour alarm path.

### Browser Tests

- Use three independent browser contexts in one online game.
- Verify per-seat privacy, setup, normal turns, robber/seven flow, building, ports, development cards, player trade, and game completion.
- Verify Commerce Guild redemption, token transfer, sealed bids, blind-box privacy, and no-bid exit.
- Verify disconnect/reconnect, English/Chinese switching, desktop/mobile containment, and Local Game regression.

## Deployment Sequence

1. Add Wrangler configuration and the initial SQLite Durable Object migration.
2. Build and verify the combined static-assets/Worker project locally.
3. Upload a Cloudflare preview version and verify real WebSockets, SQLite restoration, and hibernation recovery.
4. Connect the GitHub repository and `main` branch to Workers Builds.
5. Verify the production address.
6. Update both READMEs and stop GitHub Pages from publishing a competing production application.

## Success Criteria

- Three or four anonymous players can create, join, ready, and complete a full online game including the Commerce Guild expansion.
- Refresh and temporary disconnect preserve seat identity and current state in the original browser for up to 24 hours.
- No browser receives opponents' private resource types, development-card identities, hidden victory points, or unresolved/losing bid amounts.
- No browser can choose random outcomes, impersonate another seat, execute a stale command, or repeat an accepted command.
- All-zero Commerce Guild auctions have a deterministic path to completion in both Local Game and Online Game.
- Local hot-seat play remains operational and independent of Cloudflare connectivity.
- The verified production application is served as one Cloudflare Worker deployment built from GitHub.

## Risks and Explicit Trade-offs

- Anonymous identity cannot recover a seat on a new device; accounts are deliberately deferred.
- A user with script execution in the application origin could read `localStorage`; strict CSP and avoiding third-party scripts reduce but do not eliminate this browser threat.
- Complete projections use more bandwidth than patches but materially simplify privacy review, reconnection, and version correctness for the current state size.
- Supporting the full Commerce Guild expansion in the first online release increases the test surface; implementation must still be delivered in independently verifiable room/core and guild-privacy task groups.
- Existing `gameReducer.ts` is an 804-line integration owner. The implementation must extract match transitions and reduce its responsibility rather than add networking or projection logic to it.
